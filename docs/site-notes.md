# 사이트 기능별 세부

`docs/project-context.md`에서 옮겨 온 기능별 메모다. CLAUDE.md가 늘 싣는 파일에서 뺐다(워크스페이스 '모델·에이전트·토큰 규칙' — 늘 실리는 내용은 작게).
통째로 읽지 않는다. 고칠 기능 이름(예: `구매 차단`, `회원 탈퇴`, `반품`)으로 `grep -n` 해서 그 줄만 읽는다. 기능을 바꾸면 그 줄을 같이 고친다.

- 결제·로그인(2026-10-26, feat/two-click-checkout): **두 번 클릭 구매** — 바(수량+`총액 · 구매하기`) → 로그인 시트(카카오·네이버 + '이메일로 로그인' 링크 → `/login?next=…&email=1`) → 재구매 시트(주소·수단·메모 미리 채움) → 결제창 → `/pay/complete`(승인) → 완료. 첫 구매·주소 변경은 `/checkout` 한 화면(Daum 우편번호 레이어). 게스트 주문 없음(결정 1). 라우트 추가: `/auth/[provider]/callback` · `/auth/consent` · `/auth/mock/[provider]`(개발 대역) · `/pay/complete` · `/pay/fail`.

- 회원 탈퇴(2026-11-11, #334): 계정 화면 맨 아래 글자 링크 '회원 탈퇴' → 확인 시트(`components/account/WithdrawSheet` — 지우는 것, 법에 따라 보관하는 것(주문·결제·배송 기록 5년·취소·반품·교환 기록 3년), '출시 알림도 그만 받을게요'(`leaveWaitlist`), '안내를 확인했어요'를 체크해야 `danger` '탈퇴하기'가 열린다) → API `POST /me/withdrawal`(`api.withdrawAccount`, 세션은 `useAuth().withdraw`). 끝나지 않은 주문·신청이 있으면 서버가 409 `ACCOUNT_WITHDRAWAL_BLOCKED` 로 막는다 — 진행 중 안내 + 주문 내역 링크. 그 밖의 실패(관리자 계정 403 `ACCOUNT_WITHDRAWAL_ADMIN_FORBIDDEN` 포함)는 다시 시도 안내 — 다시 누르면 서버가 남은 일을 이어서 끝낸다(지우다 멈춘 계정은 로그인은 되지만 서버가 주문을 403 `ACCOUNT_WITHDRAWING` 으로 막는다 — 주문서는 일반 오류 문구). 지우는 것의 소셜 줄은 'suaci에 저장된 … 연결 정보' — 카카오·네이버 쪽 연결은 서버가 끊지 못할 수 있어(완료 메일이 끊는 방법을 안내) 우리가 가진 것만 말한다. 되면 로그인 토큰과 저장된 배송 메모를 지우고 홈 `/?withdrawn=1` 로 가 구매 바 위에 '탈퇴가 끝났어요.'(`account/WithdrawnNotice`). 시트는 계정 내용 밖에 둔다 — 탈퇴 뒤 로그인이 비워져도 홈으로 넘어갈 때까지 남아야 시트가 쌓은 기록 칸을 홈이 차지한다.
- 화면 공통(2026-11-04 UX 고도화): 누르는 자리 44px, 글자 최소 12px(구역 이름·합계 13~15px). 버튼은 `ui/Button`·링크 버튼은 `ui/ButtonLink` — variant `primary`(화면 목적 하나만, 먹색 채움 — 라임 채움은 쓰지 않는다)·`secondary`(테두리)·`text`(글자 링크)·`danger`(빨강, 확인 단계 필수). 상태 표시는 `ui/Badge`(작고 각지게, 누를 수 없음 — tone neutral·done·muted·problem), 고르기 칩은 `pay/chip.ts`, 배송 메모는 `pay/MemoPicker`(값은 한국어, 화면 이름만 언어별 `pay.memo.*`), 결제수단 이름 `pay.method.*`(브랜드페이 가칭 포함). 결제 결과 화면은 `pay/PayResult`. '결제하지 않은 주문이 있어요 · 이어서 결제하기'는 구매 바 바로 위 `pay/ResumePrompt`(보류 주문만 — 장바구니 없음). 로그인해야 보이는 화면(계정·배송지·주문)의 로그인 안내는 `shell/LoginRequired` 하나. API 401 은 게이트웨이 거절(본문에 코드 없음)까지 `AUTH_REQUIRED` 로 읽고, 화면은 `isAuthRequired`(`@/lib/api`)면 세션을 다시 확인해 '로그인이 풀렸어요'로 넘어간다. 데이터를 받는 화면은 같은 틀의 뼈대(`ui/Skeleton`) — 주문 목록·상세·계정·배송지는 손님 토큰이 브라우저에만 있어 서버에서 못 받으므로 뼈대, 약관·이벤트 목록은 서버에서 받는다. 빈 상태는 받은 뒤에만. 라임 위 글자는 먹색, 라임 글자 없음.
- 구매 흐름은 출시 전에도 연다(2026-11-03 오너, 토스 카드 심사): 구매 바 → 로그인 → 주문서·재구매 시트까지 누구나 간다. 결제를 받을 수 있는지는 결제창(어댑터)이 있는지로만 정한다(`canTakePayment`, `lib/payment/providers`). 없으면(운영 + 토스 키 전) 결제 버튼이 '결제 준비 중'으로 멈추고 주문을 만들지 않는다. 구매 바 위 안내는 '판매 준비 중이에요 · 출시 알림 신청'. 주문은 장바구니 없이 바로 구매(`createOrder` 의 `items`, 2026-11-06 — `lib/cart`·카트 API 메서드 제거). 결제 시작(배송 메모 기억 → 주문 만들기·30분 보류 주문 멱등키 이어 쓰기 → 결제창)은 `lib/payment/start-payment` 한 곳을 주문서·재구매 시트가 같이 쓴다(메모 저장 `lib/checkout/memo`, 이 창의 결제창 `browserPaymentAdapters`). 시작하지 못하면 두 화면 모두 같은 문구(`pay/orderError` → `checkout.error.*`). 문구 기준은 suaci-docs `research/2026-11-06-ux-copy-audit.md` 3절(몰 표준어, 해요체). 상품정보제공 고시(화장품 11칸)는 제품 섹션 맨 앞 접이 칸(펼친 채) — 값은 `constants/product-notice` 한 곳, 정하지 못한 칸은 사유('상품 입고 후 표시 예정' 등, 고시 Ⅱ.3)를 보이고 출시 전에 다 채운다(2026-11-09 UX 리뷰 A5). 사용법도 그 값을 쓰고 정해지기 전엔 칸을 숨긴다. 전성분의 향료 알레르기 유발 성분은 바로 아래 따로 한 줄. 전성분은 `constants/ingredients`(1차 전성분표 32개 + 향료 속 리모넨·리날룰, 처방이 바뀌면 그 줄만) — 한국어 화면은 한글 이름, 영어·일본어는 INCI. 결제창 주문명은 '상품 이름 N개'. `/pay/fail` 은 토스 `code` 로 취소·카드사 거절·그 밖을 나눠 우리 문구로 보여 준다(토스 `message` 는 쓰지 않는다 — 실패 주소는 누구나 만들 수 있다, `lib/payment/fail-reason`). `/pay/complete` 는 서버가 결제를 닫은 실패(OUT_OF_STOCK·ORDER_NOT_PAYABLE·PAYMENT_AMOUNT_MISMATCH)면 다시 확인하기 대신 '취소해 돌려드려요(3~7영업일)' + 그 주문 상세·홈(ORDER_NOT_PAYABLE 인데 주문을 읽어 보니 이미 결제됐으면 바로 주문 상세로). 승인 안 됨은 셋으로 나눈다 — 카드사·은행 거절(PAYMENT_DECLINED)은 '다른 결제수단으로', 결제창 인증 10분이 지남(PAYMENT_SESSION_EXPIRED)과 승인 요청 금액이 주문과 다름(PAYMENT_AMOUNT_INVALID, 2026-11-10 #328 P16 — 서버가 토스를 부르지 않음)은 '결제된 금액은 없어요 · 다시 결제하기'(모두 같은 보류 주문으로 결제창을 새로 연다). 그 밖(일시 오류)만 '다시 확인하기'. 결제 대기 주문의 '주문 취소'는 서버가 닫기 전에 토스를 본다 — 이미 승인됐으면 ORDER_ALREADY_PAID 로 알리고 화면이 주문을 다시 읽어 결제된 주문(취소 요청)으로 보인다(2026-11-10 #326). 승인 처리 중(PAYMENT_IN_PROGRESS)·토스를 못 읽음(503)이면 닫지 않고 그 버튼의 말(`orders.cancelError.*`)로 알린다 — 취소 요청(환불)의 503 과 뜻이 달라 `claims.error` 에 두지 않는다. 자동 환불 중(결제 refunding)인 주문은 status 가 pending 이어도 '환불 처리 중'이고 결제하기·취소 버튼이 없다. 이어 쓴 보류 주문이 이미 결제됐으면 결제창 대신 그 주문 상세로. 시트(로그인·재구매·take four)는 X·바깥·Esc·폰 뒤로가기로 닫힌다(`hooks/useCloseOnBack` — 열 때 기록 한 칸, 시트 안에서 다른 화면으로는 replace). 주문 상태 이름 하나는 서버가 정해 주문에 싣는다(API `state` — 결제 대기·결제완료·상품준비중·배송중·배송완료·반품 진행 중·교환 진행 중·환불 처리 중·부분환불·환불완료·주문취소. 주문·결제·배송 세 축을 접는 규칙은 suaci-api `shared/display-state` 한 곳이고 관리 툴의 '고객 화면' 표시·메일도 그 규칙을 쓴다, 2026-11-11). 목록과 상세가 같은 이름을 보인다 — 목록도 반품·교환을 나눠 '반품 진행 중'·'교환 진행 중'. 화면은 그 이름의 문구(`orders.state.*` — 키가 상태 이름과 정확히 같은지 `orders/orderState.test` 가 지킨다)·뱃지 색·진행 단계만 정한다(`orders/orderState` — 진행 단계는 배송 축에서 읽어 상태가 반품·환불을 말할 때도 보인다). 취소 요청·반품·교환·배송지 변경 버튼을 보일지는 `lib/claims/rules` 가 결제·배송 축으로 정한다(서버와 같은 조건). 배송 단계는 관리 툴이 바꾼다(2026-11-07). 발송기한(API `shipBy`, 결제한 날부터 3영업일째 끝 — 보낼 주문만, 테스트 결제는 없음)이 지났는데 아직 안 보냈으면 상태 아래 발송 지연 안내(준비되는 대로 보냄·발송 전 '주문 취소 요청'이면 전액 환불 — 그 버튼이 있을 때만, 같은 날
